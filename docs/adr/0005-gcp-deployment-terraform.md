# ADR-0005: Deploy to GCP with Terraform on managed services

**Status:** Accepted (not yet applied to a live project)

## Context
The case study runs locally and in Codespaces through Docker Compose. A cloud deployment should show the target
runtime without changing application code, and keep infrastructure reviewable and repeatable.

## Decision
- Infrastructure is code in `infra/terraform`, using one root module with the Google, Confluent and MongoDB Atlas
  providers. Versions are pinned in `.terraform.lock.hcl`. CI runs `fmt -check` and `validate`.
- Cloud Run hosts the container with one instance always on and CPU always allocated. The app is a long-lived Kafka
  consumer with a scheduler, not a request-only service.
- Cloud SQL PostgreSQL keeps the current state. It has only a private IP, reached over Direct VPC egress, with TLS
  required.
- Confluent Cloud provides Kafka and MongoDB Atlas provides the audit store, both on GCP in the same region. Terraform
  creates the topics and the application's least-privilege ACLs and database user.
- Secrets are generated by Terraform and kept in Secret Manager. The Cloud Run service account can read only those
  secrets. Kafka SASL settings are injected as `SPRING_APPLICATION_JSON`, so `application.yml` is unchanged.

## Consequences
- One `terraform apply` and one `terraform destroy` cover all three clouds. Terraform state then holds secrets and
  must live in a protected GCS backend for shared use.
- Demo defaults (public invoker, Atlas `0.0.0.0/0`, small zonal database) trade security and availability for
  cost. The production settings are listed in `infra/terraform/README.md`.
- More than one Cloud Run instance would run the nightly expiry on each replica. It is idempotent (ADR-0004), but
  ShedLock is the production follow-up.
